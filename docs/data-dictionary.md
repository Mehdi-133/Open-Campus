# Open Campus — Data Dictionary

## 1. Purpose

This document defines the data structure of the Open Campus LMS.

Open Campus uses MongoDB as its database. Therefore, the data model uses:

- **Collections** instead of tables;
- **Documents** instead of rows;
- **Fields** instead of columns;
- **ObjectId references** to represent relationships between separate collections when appropriate;
- **Embedded objects/arrays** when data naturally belongs inside a document.

The global LMS contains nine main collections:

1. `users`
2. `courses`
3. `modules`
4. `resources`
5. `enrollments`
6. `progress`
7. `quizzes`
8. `quizAttempts`
9. `feedbacks`

> The complete LMS is represented in the data dictionary and UML.
>
> The current implementation scope remains limited to `courses`, `modules`, and `resources`.

# 2. Collection — `users`

## Description

Stores registered users of Open Campus.

A user has one main role:

- `learner`
- `trainer`
- `admin`

A Visitor is not stored as a user because a visitor represents an unauthenticated actor.

## Fields

| Field | MongoDB Type | Required | Constraints / Values | Description |
|---|---|---:|---|---|
| `_id` | ObjectId | Yes | Unique, generated by MongoDB | Unique user identifier |
| `name` | String | Yes | — | User's full name |
| `email` | String | Yes | Unique | User's email address |
| `password` | String | Yes | Must be securely stored | Secured user password |
| `role` | String | Yes | `learner`, `trainer`, `admin` | Main user role |
| `status` | String | Yes | To be defined | Account status |
| `createdAt` | Date | Yes | Automatically generated | Account creation date |

## Business Rules

- A user has one main role.
- Email must be unique.
- Passwords must never be stored in plain text.
- Learners, trainers, and administrators are represented by the `role` field.
- Visitors are not stored in the `users` collection.

# 3. Collection — `courses`

## Description

Stores the learning courses available on Open Campus.

A course represents a complete learning path composed of ordered modules.

## Fields

| Field | MongoDB Type | Required | Constraints / Values | Description |
|---|---|---:|---|---|
| `_id` | ObjectId | Yes | Unique, generated by MongoDB | Unique course identifier |
| `title` | String | Yes | — | Course title |
| `shortDescription` | String | Yes | — | Short description for the catalogue |
| `description` | String | Yes | — | Detailed course description |
| `objectives` | Array<String> | Yes | — | Learning objectives |
| `prerequisites` | Array<String> | No | — | Recommended prerequisites |
| `level` | String | Yes | Values to be defined | Course difficulty level |
| `category` | String | Yes | — | Course category |
| `estimatedDuration` | Number | Yes | Positive value | Estimated course duration |
| `status` | String | Yes | `draft`, `published` | Publication status |
| `trainerId` | ObjectId | Yes* | Reference → `users._id` | Responsible trainer |
| `createdAt` | Date | Yes | Automatically generated | Course creation date |
| `publishedAt` | Date | No | Nullable | Course publication date |

## References

`trainerId` references:

`users._id`

## Business Rules

- A course has one responsible trainer.
- A trainer can be responsible for several courses.
- A course can be `draft` or `published`.
- Only published courses are publicly visible.
- A course contains one or more ordered modules.
- `publishedAt` represents the publication date.

> `trainerId` belongs to the global model. Its temporary handling must be decided while the `users` collection is outside the current implementation scope.

# 4. Collection — `modules`

## Description

Stores the modules that compose courses.

Modules are ordered to represent the learning sequence of a course.

## Fields

| Field | MongoDB Type | Required | Constraints / Values | Description |
|---|---|---:|---|---|
| `_id` | ObjectId | Yes | Unique, generated by MongoDB | Unique module identifier |
| `courseId` | ObjectId | Yes | Reference → `courses._id` | Parent course |
| `title` | String | Yes | — | Module title |
| `description` | String | Yes | — | Module description |
| `order` | Number | Yes | Positive integer | Position inside the course |
| `estimatedDuration` | Number | Yes | Positive value | Estimated module duration |
| `status` | String | Yes | To be defined | Module status |

## References

`courseId` references:

`courses._id`

## Business Rules

- A module belongs to exactly one course.
- A course contains one or more modules.
- Modules are ordered inside their course.
- `order` determines the module's position in the learning sequence.
- Whether `order` must be unique inside a course must be validated.

# 5. Collection — `resources`

## Description

Stores educational resources associated with modules.

A resource can represent learning content such as:

- article;
- video;
- external link;
- PDF;
- image;
- exercise;
- repository;
- uploaded course material.

## Fields

| Field | MongoDB Type | Required | Constraints / Values | Description |
|---|---|---:|---|---|
| `_id` | ObjectId | Yes | Unique, generated by MongoDB | Unique resource identifier |
| `moduleId` | ObjectId | Yes | Reference → `modules._id` | Parent module |
| `title` | String | Yes | — | Resource title |
| `type` | String | Yes | Resource type | Type of educational resource |
| `url` | String | Conditional | Valid URL when applicable | External resource URL |
| `fileReference` | String | Conditional | — | Uploaded file storage reference |
| `description` | String | No | — | Resource description |
| `originalFilename` | String | No | File resources | Original uploaded filename |
| `fileSize` | Number | No | Positive value | Uploaded file size |
| `estimatedDuration` | Number | No | Positive value | Estimated consultation duration |
| `order` | Number | Yes | Positive integer | Position inside the module |

## References

`moduleId` references:

`modules._id`

## Business Rules

- A resource belongs to exactly one module.
- A module can contain multiple resources.
- Resources are ordered inside their module.
- URL-based resources can use `url`.
- File-based resources can use `fileReference`.
- File metadata is relevant only for uploaded resources.
- Whether `order` must be unique inside a module must be validated.
- Protected resources must not be exposed publicly without authorization.

# 6. Collection — `enrollments`

## Description

Stores the enrollment of learners in courses.

`Enrollment` is represented as its own collection because the relationship between a learner and a course contains business information such as enrollment date, status, and progress.

## Fields

| Field | MongoDB Type | Required | Constraints / Values | Description |
|---|---|---:|---|---|
| `_id` | ObjectId | Yes | Unique, generated by MongoDB | Unique enrollment identifier |
| `learnerId` | ObjectId | Yes | Reference → `users._id` | Enrolled learner |
| `courseId` | ObjectId | Yes | Reference → `courses._id` | Enrolled course |
| `enrolledAt` | Date | Yes | — | Enrollment date |
| `status` | String | Yes | To be defined | Enrollment status |
| `globalProgress` | Number | Yes | Calculated by backend | Overall course progress |

## References

`learnerId` references:

`users._id`

`courseId` references:

`courses._id`

## Business Rules

- A learner can enroll in several courses.
- A course can have several enrolled learners.
- A learner cannot have two active enrollments for the same course.
- Enrollment concerns published courses.
- Global progress is calculated by the backend.

## Conceptual Relationship

`User (Learner) → Enrollment → Course`

Enrollment resolves the conceptual many-to-many relationship between learners and courses.

# 7. Collection — `progress`

## Description

Stores learner progress through course content.

Progress can concern a course, module, and optionally a specific resource.

## Fields

| Field | MongoDB Type | Required | Constraints / Values | Description |
|---|---|---:|---|---|
| `_id` | ObjectId | Yes | Unique, generated by MongoDB | Unique progress identifier |
| `learnerId` | ObjectId | Yes | Reference → `users._id` | Learner concerned |
| `courseId` | ObjectId | Yes | Reference → `courses._id` | Course concerned |
| `moduleId` | ObjectId | Yes | Reference → `modules._id` | Module concerned |
| `resourceId` | ObjectId | No | Reference → `resources._id` | Optional resource concerned |
| `status` | String | Yes | To be defined | Progress status |
| `startedAt` | Date | No | — | Date the content was started |
| `completedAt` | Date | No | Nullable | Date the content was completed |

## References

`learnerId` references:

`users._id`

`courseId` references:

`courses._id`

`moduleId` references:

`modules._id`

`resourceId` optionally references:

`resources._id`

## Business Rules

- Progress belongs to a learner.
- Progress concerns a course and module.
- Progress may optionally concern a specific resource.
- Progress calculations are performed by the backend.
- Progress data should allow learners to resume their learning path.

🟡 Future implementation.

# 8. Collection — `quizzes`

## Description

Stores simple assessments associated with modules.

A module may contain a quiz used to evaluate learner understanding.

## Fields

| Field | MongoDB Type | Required | Constraints / Values | Description |
|---|---|---:|---|---|
| `_id` | ObjectId | Yes | Unique, generated by MongoDB | Unique quiz identifier |
| `moduleId` | ObjectId | Yes | Reference → `modules._id` | Associated module |
| `title` | String | Yes | — | Quiz title |
| `questions` | Array<Object> | Yes | Embedded question documents | Quiz questions |
| `passingScore` | Number | Yes | Score threshold | Minimum score required |
| `status` | String | Yes | To be defined | Quiz status |

## References

`moduleId` references:

`modules._id`

## Embedded Question Structure

The exact implementation will be defined when Quiz enters the development scope.

Conceptually, a question contains:

| Field | MongoDB Type | Description |
|---|---|---|
| `text` | String | Question text |
| `choices` | Array | Available choices |
| `correctAnswer` | Value / Reference | Correct answer information |

## Business Rules

- A quiz belongs to one module.
- A module may contain a quiz.
- A quiz contains questions and possible answers.
- Correct answers must not be exposed to learners before evaluation.
- Quiz scores are calculated by the backend.

🟡 Future implementation.

# 9. Collection — `quizAttempts`

## Description

Stores attempts made by learners on quizzes.

Each document represents one learner submission for one quiz.

## Fields

| Field | MongoDB Type | Required | Constraints / Values | Description |
|---|---|---:|---|---|
| `_id` | ObjectId | Yes | Unique, generated by MongoDB | Unique attempt identifier |
| `learnerId` | ObjectId | Yes | Reference → `users._id` | Learner making the attempt |
| `quizId` | ObjectId | Yes | Reference → `quizzes._id` | Attempted quiz |
| `answers` | Array | Yes | Submitted answers | Learner responses |
| `score` | Number | Yes | Calculated by backend | Obtained score |
| `result` | String / Boolean | Yes | Passed / failed | Attempt result |
| `submittedAt` | Date | Yes | — | Submission date |

## References

`learnerId` references:

`users._id`

`quizId` references:

`quizzes._id`

## Business Rules

- A QuizAttempt belongs to one learner.
- A QuizAttempt belongs to one quiz.
- A learner may make multiple quiz attempts unless a future rule limits the number.
- A quiz may have attempts from multiple learners.
- Scores are calculated by the backend.

🟡 Future implementation.
